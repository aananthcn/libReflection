# 0013 — DWARF-Based Reflection Generation

**Status:** Implemented and verified end to end — on the Linux host,
via the QNX SDP 8.0 cross-toolchain, and by actually running on a real
QNX 8.0 aarch64 device. Built, tested (25 Python tests across the two
test files, including real compiles), and proven on
`tutorials/01_hello_world`: a plain aggregate, a class with a
user-declared constructor and private members, a class with only
public members, and a type added *after* the pipeline was already
wired up all resolve their real name/member names/offsets with **zero
annotation**, from a single `cmake --build`. See "What was actually
built" below for what differs from the original plan below it, and the
real bugs found while building it (kept, not smoothed over, per this
project's practice throughout). See "Verified on QNX SDP 8.0" below for
the cross-compilation results, the one real bug that testing found, and
the on-device execution results.

## Context

[0012](0012-generated-reflection-names.md) was reverted because its
scope — plain aggregates only, no private members — was wrongly
assumed to be representative of a real ~10,000-class legacy codebase.
It isn't: ordinary encapsulation (private data behind a constructor
and accessors) is the *typical* shape of a hand-written C++ class, and
no macro-based mechanism, hand-written or generated, can reach a
private member without a `friend` declaration inside the class — a
source modification, which is exactly the constraint ruled out from
the start (the original authors of the legacy codebase won't accept
changes to their headers).

The question this ADR answers: is there *any* way to reflect an
arbitrary class — including its private members — without modifying
its source at all? The answer explored here is yes, via DWARF debug
information.

## Why DWARF specifically

C++ access control (`public`/`private`/`protected`) is a **compile-time,
source-level** concept only. At the ABI/binary level there is no such
thing as "private data" — the memory layout is identical regardless of
access, and a debugger can already inspect a private field
(`gdb`'s `print obj.private_field` works, `ptype` shows it) because
DWARF debug info — generated by the compiler specifically so debuggers
can do this — records every data member's name, type, and offset
*regardless of its declared access*. Unlike every mechanism considered
so far (source-text scanning, hand-written macros using `decltype`/
`offsetof` as C++ *expressions*), reading DWARF never asks the C++
compiler's access checker anything at all — it reads compiler-emitted
metadata about the compiled result, after the point where access
control could object.

### Verified before deciding

Before committing to this direction, the core claim was checked
directly rather than assumed (this project's approach throughout: see
[0001](0001-reflection-generation-strategy.md)'s empirically-discovered
array/empty-struct edge cases, and [0012](0012-generated-reflection-names.md)'s
own "mistake made and fixed" for why this matters here specifically).
Compiling

```cpp
class EncapsulatedPoint {
public:
    EncapsulatedPoint(int x, int y) : x_(x), y_(y) {}
    int GetX() const { return x_; }
private:
    int x_;
    float y_;
};
```

with `g++ -g -gdwarf-4 -c` and inspecting the object file with
`objdump --dwarf=info` shows exactly the needed data, for both private
members, with no special flags or workarounds:

```
DW_TAG_class_type: DW_AT_name: EncapsulatedPoint, DW_AT_byte_size: 8
  DW_TAG_member: DW_AT_name: x_, DW_AT_type: int,   DW_AT_data_member_location: 0
  DW_TAG_member: DW_AT_name: y_, DW_AT_type: float, DW_AT_data_member_location: 4
```

No `DW_AT_accessibility` tag is even present for `x_`/`y_` (private is
the default for `class` in the DWARF spec, same as in C++) — but the
name, type, and exact byte offset are there unconditionally. This is
qualitatively different from every prior approach: it's compiler-
verified ground truth about the actual compiled layout, not a
source-text guess subject to C++ access control.

## The real risk, and how the design addresses it

Every macro-based approach so far (hand-written or generated) computes
a member's offset via `offsetof()` **in the same compilation** that
produces the real binary — self-consistent by construction, impossible
to drift. A DWARF-based approach is different: it must read debug info
from *some* compiled object, then bake the resulting offsets into
*generated code* as literal numbers (since the generated code can no
longer write `offsetof(ReflectedT, private_field)` — that's still a
C++ expression, still access-checked, still fails to compile for a
private member). If the object used for **extraction** and the object
that ends up in the **real binary** are ever compiled differently —
different flags, different compiler version, different struct packing
—  those literal offsets could silently drift from the truth. For a
library whose stated purpose is trustworthy layout info for
shared-memory IPC, silently-stale hardcoded offsets is a new and
serious failure mode that none of the prior designs had.

**Planned mitigation:** don't run a *separate* "extraction-only" compile
with potentially different settings — compile the real translation
unit, with the real target's exact compile flags (mirrored via CMake
generator expressions reading the actual target's `COMPILE_OPTIONS`/
`COMPILE_DEFINITIONS`/`INCLUDE_DIRECTORIES`), with `-g` added, so the
extraction object and the real object can't legitimately disagree on
layout.

**What was actually built is simpler, and weaker on this specific
guarantee — see "What was actually built" below for why, and for this
as a recorded, not-yet-closed risk** rather than a solved one. The
implementation compiles a separate, auto-generated "driver" file with
an explicit, fixed flag set (`-std=c++20 -g -gdwarf-4` plus a couple of
`-I` paths) rather than mirroring the real target's full compile
properties via generator expressions. For everything this ADR has been
verified against so far (plain structs, single-TU classes, no custom
`-D` defines or non-default struct-packing pragmas) this is
equivalent, but it is not the same *guarantee* the design above
describes, and shouldn't be presented as such.

## Automating both the annotation and compilation steps

Per the explicit requirement for this ADR: both steps must be
automated, not manual. (This section is the original plan; see
"What was actually built" below for the mechanism as it was actually
implemented and verified — the "touch every type" step in particular
turned out to need real work, not just a `sizeof`, to reliably force
full DWARF emission.)

- **No annotation step at all** for the type itself — that's the whole
  point of DWARF over the prior text-scanning approach: no `friend`
  declaration, no `REFLECT_CLASS_BEGIN`, nothing written in or near
  the original source, public or private members alike.
- **The compilation/extraction step is a CMake-orchestrated pipeline**,
  not a manual step a human runs:
  1. A CMake function compiles a small extraction translation unit
     (the target header(s) plus a trivial "touch every type" body so
     the types are actually instantiated/emitted, not just declared)
     using the **real target's** compile settings plus `-g`.
  2. A post-compile step parses the resulting object's DWARF (via
     `objdump --dwarf=info`/`readelf --debug-dump=info` — see "Tooling
     choice" below) and generates a reflection-registration header
     from the ground-truth name/type/offset/size data, the same
     `REFLECT_CLASS_BEGIN`-shaped output already proven safe, except
     now with `m.offset = <literal from DWARF>;` instead of
     `offsetof(...)`, and `m.name = "<literal from DWARF>";` directly
     (no `decltype`/access-checked expression needed for either, since
     neither is now a checked expression — this is the mechanism that
     makes private members reachable at all).
  3. That generated header is compiled into the real target, same
     `add_custom_command` + generated-file-as-target-source pattern
     already used and proven in [0012](0012-generated-reflection-names.md)
     (minus the now-reverted parts).
  All three steps are ordinary CMake build steps, rerun automatically
  whenever the source changes — a developer runs `cmake --build` once,
  same as today.

## Tooling choice: `objdump`/`readelf` text output, not a new Python package

Three ways to read DWARF were considered:

1. **`pyelftools`** (pure Python, pip-installable) — the most direct
   programmatic access, but a *new* Python package dependency beyond
   the standard library, on top of Python 3 itself already being a
   new host dependency from [0012](0012-generated-reflection-names.md)'s
   era.
2. **A hand-rolled DWARF parser reading raw `.debug_info`/`.debug_abbrev`
   ELF sections** — no new dependency at all, but DWARF's abbreviation-
   table/form encoding is genuinely complex to get right from scratch;
   high effort, high risk of subtle bugs, for something a standard tool
   already does correctly.
3. **Parse `objdump --dwarf=info` or `readelf --debug-dump=info`'s
   text output** — no new dependency: both ship with the C/C++
   toolchain already required to build this project (GNU binutils on
   Linux; the QNX SDP 8.0 cross-toolchain ships its own equivalents).
   The output format is a long-established, versioned CLI convention
   (not a compiler-internal debug format like `__PRETTY_FUNCTION__`)
   used by many existing scripts and tools already.

**Decision: option 3.** It's the only one that adds zero new
dependencies beyond what building this project already requires on
either target platform, while still getting genuine ground-truth data
(the *source* of the data — DWARF — is what makes this reliable; how
it's read back out is a secondary, much lower-risk concern by
comparison). `pyelftools` remains a reasonable fallback if the text
format proves harder to parse robustly than expected in practice.

## What was actually built

Implemented, tested, and demonstrated on `tutorials/01_hello_world`
(a plain aggregate `HelloWorld`, a non-aggregate-with-private-members
`PoorPoint`, a public-member `BetterPoint`, and — added *after* the
pipeline was already wired up, to prove the workflow — `Widget`, all
resolving correctly from one `cmake --build`):

- **Type discovery is fully automatic**, not part of the original
  design above: `tools/generate_dwarf_reflection.py`'s
  `discover_type_names()` scans `SOURCE`, and every local
  (`"..."`, never `<...>`) header it `#include`s transitively, for
  top-level `struct`/`class` declarations via a plain regex — no
  CMake-level type list needed anywhere. It only needs to find NAMES;
  DWARF (not this scan) handles everything about what's inside them,
  which is why it can stay this simple without repeating
  [0012](0012-generated-reflection-names.md)'s member-body-parsing
  fragility.
- **Forcing full DWARF emission needed more than expected, found
  empirically:**
  - `sizeof(Type)` in a `constexpr`/unevaluated context is **not**
    sufficient — GCC was observed to omit the full `DW_TAG_class_type`/
    `DW_TAG_structure_type` DIE entirely when nothing but `sizeof`
    touches the type. An actual global *instance* of the type is what
    reliably forces full emission (verified).
  - But a plain `Type touch_Type;` only compiles for
    **default-constructible** types — which fails for exactly the
    encapsulated-with-required-constructor-arguments shape this ADR
    exists for. Fixed with a wrapper union with an explicit no-op
    default constructor/destructor:
    `union Touch_Type { Type value; char dummy; Touch_Type():dummy(0){} ~Touch_Type(){} };`
    — verified this compiles for a type whose only constructor takes
    arguments, and still forces full DWARF emission of the member.
  - A bare `template <typename T> struct Box {...};` matches the same
    discovery regex but can't be touch-instantiated without knowing
    `T` — discovery now explicitly excludes a `struct`/`class` name
    immediately preceded by a `template<...>` parameter list.
- **Text-scanning pitfalls, caught by the tests written against them**
  (this scanner's job is far narrower than [0012](0012-generated-reflection-names.md)'s
  — find names, never understand a body — but still needed care):
  - A log-message-shaped string literal like `"class name: X"` was
    matched as a fake type declaration before comments/string/char
    literals were stripped from the scanned text.
  - `#include "HelloWorld.hpp"` was silently turned into
    `#include ""` by that *same* string-literal-blanking step, since
    an include path uses identical quote syntax to a string literal
    but means something else entirely — fixed by extracting
    `#include` lines from a comments-only-stripped copy of the text,
    kept separate from the further string/char-literal-stripped copy
    used for the actual declaration scan.
- **Generated macros never write an access-checked expression.**
  `REFLECT_DWARF_CLASS_BEGIN`/`REFLECT_DWARF_MEMBER`/
  `REFLECT_DWARF_CLASS_END` (`src/ReflectionMacros.hpp`) take name/type/
  offset/size as literal arguments — no `decltype(Type::member)`, no
  `offsetof(Type, member)` anywhere. This is precisely what lets the
  generated code reach a private member: nothing in it is subject to
  C++ access control at all.
- **`cmake/GenerateDwarfReflection.cmake`**'s `reflection_generate_dwarf(TARGET
  <t> SOURCE <src>)` runs discover → emit driver → compile driver with
  debug info → extract → generate header as ordinary
  `add_custom_command` steps, ordered via `OBJECT_DEPENDS` so `<t>`'s
  real compile of `<src>` waits for the freshly generated header —
  one `cmake --build`, no separate manual step.
- **`SOURCE` needs exactly one permanent, one-time line**:
  `#include "generated_dwarf_reflection.hpp"`, placed after all its
  type definitions (the same declare-before-use rule
  `REFLECT_CLASS_BEGIN`'s output has always been subject to — see
  [0010](0010-header-and-macro-sketch.md)). This is not per-class
  annotation; it's a one-time addition to the file, the same kind of
  boilerplate as `#include <Reflection.hpp>` itself.

## Verified on QNX SDP 8.0

The pipeline was run against a real QNX SDP 8.0 install (`/home/aananth/qnx800`,
GCC 12.2.0-based), cross-compiling `tutorials/01_hello_world` for both
`x86_64` and `aarch64` QNX targets via ordinary CMake toolchain files:

```cmake
set(CMAKE_SYSTEM_NAME QNX)
set(CMAKE_SYSTEM_PROCESSOR x86_64)   # or aarch64
set(CMAKE_C_COMPILER x86_64-pc-nto-qnx8.0.0-gcc)
set(CMAKE_CXX_COMPILER x86_64-pc-nto-qnx8.0.0-g++)
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
```

Result: `cmake --build` ran the full discover → emit-driver → compile-
with-debug-info → extract-DWARF → generate-header → real-compile
pipeline unmodified, for both targets, producing byte-identical
generated `REFLECT_DWARF_CLASS_BEGIN`/`MEMBER` output to the Linux host
build (same names, same offsets, same sizes for `PoorPoint`,
`BetterPoint`, `Widget`, `HelloWorld` — including `PoorPoint`'s private
`x`/`y`). The resulting binaries were confirmed genuine QNX executables
via `file`:

```
01_hello_world (x86_64):  ELF 64-bit LSB pie executable, x86-64, ...
                           interpreter /usr/lib/ldqnx-64.so.2, with debug_info
01_hello_world (aarch64): ELF 64-bit LSB pie executable, ARM aarch64, ...
                           interpreter /usr/lib/ldqnx-64.so.2, with debug_info
```

**One real bug found and fixed by this testing:** `dump_dwarf()` in
`tools/generate_dwarf_reflection.py` had `objdump` hardcoded as a bare
command name, run via `subprocess` and relying on `PATH`. Sourcing the
QNX SDP environment (`qnxsdp-env.sh`) does **not** put a QNX-target-
appropriate `objdump` on `PATH` under that plain name — only the host's
own `objdump` is there, which cannot read a QNX-target object's DWARF
correctly in general (different default settings/target triple).
Fixed by parameterizing `dump_dwarf()`/`extract()`/the script's CLI
with an explicit `--objdump <path>` argument, and having
`cmake/GenerateDwarfReflection.cmake` pass `${CMAKE_OBJDUMP}` (CMake's
own toolchain-resolved objdump), falling back to the bare `"objdump"`
name only if `CMAKE_OBJDUMP` is unset.

**A related finding worth calling out for anyone writing their own QNX
toolchain file for this library:** CMake's `CMAKE_OBJDUMP`
auto-detection only works reliably when the toolchain file names the
compiler using the standard GNU-triple convention (e.g.
`x86_64-pc-nto-qnx8.0.0-g++`) — CMake derives the matching
`x86_64-pc-nto-qnx8.0.0-objdump` from that name. This was verified
directly: a pre-existing QNX CMake build already on this machine, whose
toolchain file points `CMAKE_CXX_COMPILER` at a non-GNU-triple-named
compiler wrapper, has CMake silently fall back to the *host's* objdump
in `CMAKE_OBJDUMP` — a latent bug in that project, invisible until
something (like this pipeline) actually depends on `CMAKE_OBJDUMP`
being correct. `cmake/qnx-toolchain.cmake` (vendored by this library —
see [0006](0006-build-system-and-qnx-portability.md)) follows this
convention, selecting the per-target GNU-triple compiler binaries via
a plain `QNX_ARCH` environment variable (or `-DCMAKE_SYSTEM_PROCESSOR`)
rather than requiring any file edit or CMake code per target.

### Verified by running on real QNX hardware, not just cross-compiled

Beyond confirming the cross-compiled binaries' ELF format, the
`aarch64` build was copied to and executed on a real QNX 8.0 aarch64
device reachable on the network (`uname -a` on the device confirmed
`QNX ... 8.0.0 ... aarch64le`) — not a simulator, not just a format
check. Both `tutorials/01_hello_world`'s executable and the
`ReflectionTests` unit suite were copied over (`scp`) and run directly
on the device:

- `01_hello_world` printed correct output for all four types,
  including `PoorPoint`'s private `x`/`y` at the expected offsets —
  identical to the Linux-host and earlier cross-compile-only results.
- `ReflectionTests` reported **all 19 test cases passed**, natively on
  the device.

This is the strongest evidence so far that the pipeline's output is
correct where it actually matters: running, not just compiling, on the
real target. Because a real QNX 8.0 aarch64 device was available for
this, `cmake/qnx-toolchain.cmake` now defaults `QNX_ARCH` to `aarch64`
rather than `x86_64`.

## Known open risks, stated plainly

- **A direct fixed-size array member currently gets silently wrong
  data, not a skip.** `resolve_type()` has no case for
  `DW_TAG_array_type`, so it falls through to the generic branch and
  returns `("<unknown>", 0)` for an array member's type/size. Verified
  by testing:
  ```cpp
  struct WithArray { int values[3]; float f; };
  ```
  generates
  ```cpp
  REFLECT_DWARF_CLASS_BEGIN(WithArray, 16)
      REFLECT_DWARF_MEMBER("values", "<unknown>", 0, 0)   // wrong: should be 12
      REFLECT_DWARF_MEMBER("f", "float", 12, 4)
  REFLECT_DWARF_CLASS_END()
  ```
  The member's offset (`0`) is still correct — DWARF gives that
  straight from `DW_AT_data_member_location` on the `DW_TAG_member`
  itself, independent of `resolve_type()` — but the **size is wrong**
  (`0` instead of `12`), not merely missing. This is qualitatively
  different from every other unresolvable case in this file (an
  unfound type gets a `// ... skipped, not guessed.` comment and no
  generated block at all — see `extract()`) and is a real violation of
  this project's own stated principle of abstaining rather than
  guessing wrong (see [0012](0012-generated-reflection-names.md)'s
  revert and this file's "Text-scanning pitfalls" above). **Not yet
  fixed** — a type with a direct array member must still use
  `REFLECT_CLASS_BEGIN` (see README's "escape hatch" section), and this
  is a stronger reason for that than previously documented: it is not
  merely unhelped by the DWARF path, it is actively mishandled by it
  today for any project that has wired the pipeline in and happens to
  reflect such a type. Fixing this means either resolving
  `DW_TAG_array_type` correctly (element type × `DW_TAG_subrange_type`
  count) or, at minimum, making `find_type()` skip the member with a
  `// not resolved -- skipped, not guessed.`-style comment instead of
  emitting a wrong literal.

- **The extraction driver does not mirror the real target's full
  compile settings** (custom `-D` defines, non-default struct-packing
  pragmas, etc.) — it uses a fixed `-std=c++20 -g -gdwarf-4` plus a
  couple of explicit `-I` paths. For everything tested so far — including
  the QNX SDP 8.0 cross-builds above — this is equivalent to the real
  compile, but it is a weaker guarantee than the "reuse the target's
  real settings via generator expressions" mitigation originally
  planned (see "The real risk..." above) and should be tightened
  before this is trusted for a target with non-default, layout-affecting
  compile flags.
- **Templates are excluded from automatic discovery entirely** (see
  "What was actually built" above) — a templated type still needs a
  hand-written `REFLECT_CLASS_BEGIN`-style approach, or a future
  extension that knows which concrete instantiations to touch.
- **The member-ordering risk from the text-scanner era doesn't carry
  over.** [0012](0012-generated-reflection-names.md)'s one residual
  risk was two real member names supplied in the wrong order (its
  scanner only knew declaration order from source text). DWARF gives
  an explicit, unambiguous offset per named member directly — there's
  no ordering to get wrong.

## Future work: enums and array members are not the accepted final answer either

`REFLECT_ENUM_BEGIN` (always, for enum value names) and
`REFLECT_CLASS_BEGIN` (for a type with a direct fixed-size array
member — doubly so now, per the bug above) are today's remaining
escape hatches documented in README's "escape hatch" section. Per this
project's stated goal, neither should be treated as a permanent
requirement, the same way the private-member/non-aggregate case wasn't
(this ADR exists because that one was actively eliminated, not
accepted). Both are addressable by extending this same DWARF pipeline,
not a different mechanism:

- **Enums**: `discover_type_names()`'s regex only matches `struct`/
  `class`; extending it to also match `enum`/`enum class` declarations,
  and `find_type()`/`resolve_type()` to read `DW_TAG_enumeration_type`
  and its `DW_TAG_enumerator` children (each has a name and a constant
  value directly in DWARF, no access control involved), would let enum
  value names resolve with zero annotation the same way struct member
  names do today.
- **Array members**: fixing the bug above (resolving
  `DW_TAG_array_type` via its element type and `DW_TAG_subrange_type`
  count) removes the last reason a struct with an array member needs
  `REFLECT_CLASS_BEGIN` at all, once it's already covered by this
  pipeline.

Neither is done yet — recorded here so this ADR's own "Consequences"
section below isn't read as declaring these two cases solved.

## Consequences

- This is a materially bigger mechanism than [0012](0012-generated-reflection-names.md)'s
  text scanner: an extra compile pass per reflected source file, a
  DWARF text-output parser, and CMake wiring to sequence discover →
  compile → extract → generate → real-compile automatically.
- It is the only approach found so far that can reach a private member,
  or a class with a constructor requiring arguments, without modifying
  the class that owns it — directly addressing what
  [0012](0012-generated-reflection-names.md)'s revert exposed as the
  actual, common-case problem, and verified working end to end, not
  just designed.
- Enums and array members have a working fallback today
  (`REFLECT_ENUM_BEGIN`/`REFLECT_CLASS_BEGIN`, see
  [0001](0001-reflection-generation-strategy.md)) — not a solved
  problem, an unclosed one; see "Future work" above. This mechanism's
  proven value so far is specifically the case none of those reach:
  private members and non-aggregate types in source that can't be
  modified.
